# PR #997 与最新 main：四路径性能对比

## 对照版本与采集方法

远程主线锁定为 `34851b76c9986aeb9dd9826a4ca57c3ba0c205f1`，从该提交的完整源码独立标准构建 wheel；PR 为 rebase 后 `c7af2aaa` 加本轮 A2 预算/CU 校验、host 报错及 A5 X=1 两遍读取整改。没有使用早期性能包冒充本轮 main。两版各78个 so/o、72个设备对象记录 SHA256；主线使用标准打包后的合并 tiling 库，PR 使用实际验收的 host 库。API、tiling 与构建产物对应，kernel JSON sha256 与对象一致。

平台为 A5 Ascend950PR，CANN 9.2.0-beta.2，torch 2.9.0+cpu / torch_npu 2.9.0.post6；同一物理卡5、逻辑0，两个版本串行采集。设备允许共享，不停止其他任务。全部36个 issue680 模型形状，K=V=128，分别覆盖 V-first FP32/BF16 与 K-first FP32/BF16，共144组。每组3次预热、5次正式；统计目标 `RecurrentKda` 的 `Task Duration(us)`，不是 Python/host 端到端时间。out 保留整 tile 完成后批量搬出，未开启诊断插桩或 sanitizer。

采集后补齐 Python stable/ctypes 的元数据生产者等待；最终 wrapper 在两平台重新通过元数据、公开契约及三入口回归。该补充没有改变任何 host/kernel 二进制，72个正常设备对象保持一致，因此保留本次 kernel 计时；不能据此推断等待、CU/indices/accepted 快照或 Python 调用链的端到端收益。

```bash
msprof --output="$RESULT" --task-time=on python perf.py \
  --package "$PACKAGE" --case-root "$CASE_ROOT" \
  --selection selection-full.json --manifest "$MANIFEST"
```

`perf.py` 是私有证据中的固定采集脚本，使用仓内 `model_specs/build_inputs/call_options`。首轮 main→PR；逐组比较输入 spec/options/shape/stride/dtype，完全相同。两版 CSV 均2304行×48列，目标 kernel 各1152条（144×8），正式样本各720条；目标均56 block、device5。所有样本保留，不根据耗时删除。

## 解释边界

四条路径首轮均为36/36的测量均值更低；7组复核也保持更低。该结论仅对应所列平台、构建、共享状态及目标 kernel，不能当作每次调用必然加速的保证。特别是首轮 V-first FP32 最接近的组仅下降约2.51%，应结合样本波动判断。未测本轮 A2 性能，也不由此推断 A3 性能。

packed CU、活跃索引/accepted 的 host 同步/D2H/快照成本没有计入上述 kernel 时间。A2/A3 新增的 CU 校验开销在 API 中明确说明；没有把 kernel 加速比例推广到完整 Python 调用。私有证据标识为 `output/rkda-final-review-20261031/`，包括原始两轮 CSV、全部样本、输入 manifest、构建身份、设备快照、脚本及失败的准备步骤日志；不是公共下载工件。
